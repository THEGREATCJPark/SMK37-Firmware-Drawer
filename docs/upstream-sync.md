# Upstream observation and provenance

Run `node scripts/sync-upstream.mjs` to refresh six allowlisted GitHub source repositories and explicitly report VA as unknown (its publisher has no configured GitHub release source). Add `--verify-attestations` to download the unique bundled pinned artifacts (nine initially; the list follows the reviewed catalog), enforce each catalog size and SHA-256, then run `gh attestation verify FILE --repo EXACT_DISTRIBUTION_REPOSITORY --format json`. `--only-unchecked` additionally skips only complete previously verified results for an identical digest and repository, retaining previous timestamps; missing, unavailable and failed results are retried. GitHub CLI must be installed and authenticated; GH_TOKEN/GITHUB_TOKEN is supported. No remote code is executed.

`public/updates.json` is observation metadata. It never changes the reviewed installation catalog. Tags are strings, not semver comparisons or evidence that an SMK model can install a release. `pinnedVersions` describes catalog packages, not a connected device's installed version. Source and binary distribution repositories differ (notably Erik37 and the local SloopDX port); both are shown separately. The latest stable release comes only from the source repository via GitHub releases/latest; a 404 means no stable release was returned.

Requests have 20-second timeouts, at most two retries, bounded rate-limit delays and a streamed 2 MiB cap. Partial failures retain last-good release details with `status: unknown`, `stale: true`, a failed check timestamp and previous successful timestamp. A latest-stable endpoint 404 is separately `no-release`. The output is atomically replaced and bounded to 200 KB. Add `--previous-deployed` in CI to load the bounded, schema-validated snapshot exclusively from https://thegreatcjpark.github.io/SMK37-Firmware-Drawer/updates.json. Only a newer valid snapshot replaces the checked-in fallback; unavailable or malformed deployed data leaves that fallback intact. The final snapshot must also pass the same schema before atomic publication. Node 22.18 or newer is required for native TypeScript schema loading.

Attestations report `missing` only for explicit no-attestation responses, `unavailable` for infrastructure/authentication/network failures, and `failed` for verification or pinned-byte mismatch. `verified` requires successful GitHub CLI cryptographic verification scoped to the exact repository, a matching statement SHA-256, and the certificate's source repository commit. The certificate repository must match the expected repository and the verified provenance's resolved Git dependency must bind that same repository and commit. Release tags and Hub provenance fields cannot produce verified status. A later unavailable or missing lookup preserves a previous verified/failed cryptographic verdict and source commit, marks it stale, and records lastAttemptAt; a real new verification verdict can replace it. This verifies provenance, not hardware compatibility or firmware safety. Running without the verification flag retains prior immutable-digest results and their original check timestamps.

Optional `--discover-hub` reads only https://thefirmwarehub.com/catalog.json and only its small SMK37 version list; it never downloads the broad FM-1 firmware collection. It preserves any discovery check younger than 24 hours (including failed attempts, whose last-success timestamp remains separate) or `.local/hub-catalog-review.json` younger than 24 hours before fetching. Reviewed names are mapped locally; ambiguous board-port repositories remain null. These are browsing suggestions with unverified model compatibility, never install candidates. Firmware license is unknown for these aggregate SMK entries.

Firmware list: [The Firmware Hub](https://thefirmwarehub.com), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). The list's license is distinct from individual firmware licenses (often GPL-3.0). Only names/version facts are normalized; maker card prose and pictures are not copied. The feed requests at most one read per day. Schedule once daily and retain successful snapshot/cache; do not repeatedly force fresh fetches from clean environments.

Offline tests inject fetch responses and verify rate-limit failure semantics, bounded retries/streams, pinned bytes, digest binding, schema constraints and discovery trust boundaries: `npx vitest run tests/upstream-sync.test.ts`.
